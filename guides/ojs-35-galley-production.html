OJS 3.5 galley production: Word → PDF + HTML + JATS

OJS 3.5 is the current LTS line (3.5.0-6, released 2026-11-01). Its production stage expects you to supply galleys; it does not typeset your Word manuscript. This guide walks the native workflow and where a local conversion pipeline fits — including the parts that still need a human.

The native workflow

  1. Submission reaches Production after copyediting. The production editor works from the final draft files.
  2. Publication → Galleys → Add galley: give it a label (PDF, HTML, XML), upload the file, set language and rights.
  3. For HTML galleys, dependent files (images, CSS) are uploaded as dependent files of the galley.
  4. For JATS XML, OJS stores the file; rendering depends on your viewer (the Lens/eLens family has known maintenance problems — PKP staff say so plainly in the community forum).
  5. Assign galleys to the issue, set volume/issue metadata, and publish.

Producing the three formats from one Word source

A reproducible local pipeline:

  1. DOCX → HTML with pandoc (--to=html5), preserving structure: abstract, headings, tables, figures, references.
  2. DOCX → JATS with pandoc's jats_publishing writer, then insert the journal's volume/issue metadata into the XML.
  3. Validate JATS against the official Publishing 1.2 MathML2 DTD. A galley that fails DTD validation will fail downstream indexing — validate before upload, not after.
  4. HTML → PDF with a paged-media renderer (a headless browser print pipeline works; commercial engines like PrinceXML offer PDF/UA). Two-column layout, running heads, figure placement.
  5. Register the three files on the submission via OJS's galley repositories (or the UI), associate figures as dependent files, and verify stored checksums match the originals.

Verified, not asserted

This pipeline was executed end-to-end on a disposable OJS 3.5.0.4 installation: a generated DOCX produced PDF, HTML and JATS; the JATS passed the official Publishing 1.2 MathML2 DTD; all three galleys registered natively on one draft with the PNG associated as a dependent file; MIME types matched and all four files matched their original SHA-256 in OJS private storage.

Honest limits

  • Complex layouts need an editor. Free DOCX→JATS converters (including the OJS docxConverter plugin) handle simple articles; a journal editor in the PKP forum reports their journal was "too complex for it". Multi-column figures, custom floats and heavy math still need review.
  • JATS display is a separate problem. Producing valid JATS does not give you a working in-OJS viewer; plan for the viewer maintenance risk.
  • Native production is coming. PKP's lead has stated OJS will integrate an OS-APS/SciFlow-derived editor with in-browser HTML→PDF (Vivliostyle), targeted at 3.6, with DOCX import still at pilot stage as of late 2025. JATS export is not in that stated plan. Watch the 3.6 release notes before assuming any external tool is permanently necessary.
  • Version drift. Our native verification ran on 3.5.0.4; 3.5.0-6 is current. Re-run the fixture on your exact version before relying on it.

When a subscription beats per-article

Per-article services run $5–$49/article in the current market. A $59/month local pipeline breaks even against a $25/article service at roughly 3 articles/month, and against $25/article at ~29 articles/year if you only need XML — the three-format bundle plus local, editable source is what changes the math for a journal producing ~40 articles/year.
